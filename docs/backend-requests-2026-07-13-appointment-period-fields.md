# Поля периода на приёме (оплата за период) — 2026-07-13

## Контекст: как «оплата за период» работает теперь на фронте

По требованию заказчика (13.07) режим «На период» переделан. **Приёмы на каждую дату
занятия больше НЕ создаются.** Вместо этого создаётся **один обычный приём** в день
оформления, где в услуге стоит `quantity` = число занятий периода:

```json
POST /api/v1/appointments/
{
  "patient": "<uuid>",
  "appointmentAt": "2026-07-13T10:00:00+06:00",
  "services": [{ "sellableItem": "<uuid>", "performer": "<uuid>", "quantity": 12 }]
}
```

Оплата проводится обычным `PATCH /appointments/{id}/` (полная сумма за 12 занятий),
печатается один чек. Эндпоинт `POST/GET /api/v1/period-payments/` фронтом
**больше не вызывается** — вся сумма и так попадает в день оформления, потому что приём
там один. Отдельная сущность period-оплаты для этой схемы не нужна.

## Проблема: даты периода негде хранить

В чеке заказчик хочет видеть информацию об оплате за период:

```
Период с            01.08.2026
по                  31.08.2026
Занятий             12 занятий
Дни: 04.08, 06.08, 08.08, 11.08, …
```

Сейчас фронт печатает этот блок только сразу после оплаты — данные о периоде живут
в форме создания. При **повторной печати чека** из карточки приёма (кнопка «Печать чека»)
блока не будет: у приёма нет ни начала/конца периода, ни дат занятий. В ответе
`GET /appointments/{id}/` таких полей нет — восстановить их неоткуда.

## Что просим

Добавить приёму необязательные поля периода и принимать их на создание/обновление:

| поле | тип | смысл |
|---|---|---|
| `periodFrom` | `date` (YYYY-MM-DD), nullable | начало периода |
| `periodTo` | `date` (YYYY-MM-DD), nullable | конец периода |
| `periodDates` | `date[]`, nullable/пустой | даты занятий (обычно 4–30 значений, ограничение фронта — 60) |

Требуется:
1. Принимать их в `POST /api/v1/appointments/` и `PATCH /api/v1/appointments/{id}/`.
2. Возвращать в `GET /appointments/{id}/` и в списке приёмов дня (тот же сериализатор,
   что отдаёт `adminComment`, `totalAmount` и т.д.).
3. Ничего не пересчитывать по этим полям — они **только для печати чека**. Сумма, статус,
   долг и заработок специалиста считаются как у обычного приёма, по `quantity` услуги.

Для приёмов без периода поля просто `null`/пустые — фронт печатает обычный разовый чек.

## Открытые вопросы (наши догадки, подтвердите или поправьте)

1. **Имена полей.** Предлагаем `periodFrom` / `periodTo` / `periodDates` (camelCase, как
   остальной API). Если у вас уже есть похожая сущность (подписки/абонементы) — скажите,
   как называть, чтобы не плодить синонимы.
2. **`periodDates` как массив дат** — приемлемо для вашей модели, или удобнее одно поле
   (например, JSON/текст)? Фронту достаточно любого варианта, который приходит обратно.
3. **Нужны ли поля в отчётах.** Мы считаем, что нет: приём один, деньги и earned уже в дне
   оформления, отчёты трогать не нужно. Подтвердите, что не потребуется отдельная
   отчётность «по периодам».
4. **Судьба `/api/v1/period-payments/`.** Фронт его больше не использует. Оставляете как
   есть (старые оплаты) или планируете депрекейт? Нам всё равно, вопрос на вашей стороне —
   просто чтобы вы знали, что вызовов от нас больше не будет.
5. **Валидация.** Ожидаем, что бэк НЕ проверяет соответствие `len(periodDates)` и `quantity`
   услуги (админ может отредактировать приём). Если решите валидировать — предупредите,
   фронт сейчас такого соответствия не гарантирует при ручном редактировании.

## Что делает фронт после ответа

Проставляет `periodFrom/periodTo/periodDates` при создании записи на период и читает их
при печати чека (в том числе повторной). До появления полей блок периода печатается только
в момент оплаты — временное ограничение, известно заказчику.
