# Требования к бэкенду — финансовая консистентность

## Цель

Этот документ нужен, чтобы синхронизировать фронтенд и бэкенд по финансовым данным и убрать ситуации, когда:

- разные страницы показывают разные суммы денег;
- payroll-расходы попадают в разные месяцы;
- фронтенд вынужден угадывать бизнес-логику по названию категории или по косвенным данным;
- ручная сверка `/reports`, `/salary-reports`, `/cashbox`, `/expenses` становится неоднозначной.

---

## Какие страницы должны быть консистентны

- `/reports`
- `/salary-reports`
- `/cashbox`
- `/expenses`

---

## Что уже есть и подтверждено

На текущий момент в API уже есть базовые серверные агрегаты:

1. `GET /api/v1/reports/financial-monthly/`
2. `GET /api/v1/reports/payroll-monthly/`
3. `GET /api/v1/cashbox/summary/`
4. `GET /api/v1/expenses/`

Также в `cashbox` уже задокументировано важное правило:

- в приёмы попадают только записи, где `paid_cash + paid_card + paid_balance + paid_bonuses > 0`
- даже если запись `cancelled`, она учитывается, если оплата была принята

Это уже описано в OpenAPI и может использоваться как источник истины.

---

## Что критически нужно от бэкенда

### 1. Явный серверный признак payroll-расхода

Сейчас фронтенд определяет зарплатные расходы по названию категории:

- `аванс`
- `заработная плата`
- `зп`

Это ненадежно и не должно быть источником бизнес-логики.

Нужно одно из решений:

1. Поле у категории:
   - `expenseCategory.kind = payroll | operational | purchase | other`
2. Или поле у расхода:
   - `expense.kind = payroll | advance | operational | other`
3. Или отдельный флаг:
   - `expense.affectsPayrollMonth = true | false`

### Почему это важно

- фронтенд не должен решать финансовую логику по строкам;
- изменение названия категории не должно ломать месячную группировку;
- payroll и non-payroll расходы должны определяться одинаково во всех отчетах.

---

### 2. Обязательный `affectsMonth` для зарплат и авансов

Поле уже нужно фронтенду и уже отправляется при создании/редактировании расходов, но сейчас оно не описано в OpenAPI схемах `ExpenseCreate`, `ExpenseUpdate`, `ExpenseRead`.

Нужно:

1. Добавить `affectsMonth` в:
   - `ExpenseCreateRequest`
   - `ExpenseUpdateRequest`
   - `PatchedExpenseUpdateRequest`
   - `ExpenseRead`
2. Формат:
   - `YYYY-MM`
3. Валидация:
   - для payroll/advance расходов поле обязательно
   - для остальных расходов поле может быть `null`

### Почему это важно

- `/expenses` и `/salary-reports` должны относить зарплатные суммы к одному и тому же месяцу;
- `createdAt` не всегда отражает месяц учета;
- без обязательного `affectsMonth` ручная сверка зарплат и авансов остается плавающей.

---

### 3. Миграция старых payroll-расходов

Если в базе уже есть старые расходы по зарплатам/авансам без `affectsMonth`, нужна миграция.

Минимально нужно:

1. определить все payroll/advance расходы;
2. заполнить им `affectsMonth`;
3. зафиксировать правило, по какому полю этот месяц восстанавливается.

### Почему это важно

Без миграции новые записи будут считаться правильно, а старые продолжат давать расхождения между:

- `/expenses`
- `/salary-reports`
- возможно `/cashbox`

---

### 4. Единый контракт по финансовой семантике между `reports` и `cashbox`

Нужно явно зафиксировать, что именно означает каждое агрегированное поле.

Обязательно документировать:

1. Что входит в `servicesSum`
2. Что входит в `productsSum`
3. Что считается `discount`
4. Что считается `debt`
5. Что считается `totalRevenue`, если это поле появится
6. Как учитываются:
   - частичная оплата
   - бесплатные услуги
   - скидки
   - долг
   - оплата с баланса
   - оплата бонусами
   - `cancelled`, если оплата уже была принята

### Почему это важно

Сейчас страницы могут показывать разные деньги не потому, что фронтенд ошибся в арифметике, а потому что смысл агрегатов для пользователя и разработчика неочевиден.

Нужна короткая таблица-инвариант уровня API:

| Экран | Что показывает |
|---|---|
| `/reports` | выручка/долг/скидки по месяцу |
| `/cashbox` | фактический денежный поток за диапазон |
| `/salary-reports` | начисления/удержания/чистая зарплата |
| `/expenses` | список и группировка расходов по периоду учета |

---

### 5. Явная модель возвратов и корректировок

Если в бизнесе есть:

- возвраты;
- отмена оплаты;
- сторно;
- ручные корректировки;

то они должны быть явно представлены в серверной модели и агрегатах.

Нужно одно из решений:

1. отдельная сущность `financialAdjustment`
2. отдельный тип `expense/income`
3. отдельные поля в агрегатах:
   - `refundsSum`
   - `reversalsSum`
   - `adjustmentsSum`

### Почему это важно

Без этого невозможно гарантировать, что:

- `/cashbox`
- `/reports`
- `/salary-reports`

сходятся после возвратов и перерасчетов.

---

## Что желательно от бэкенда

### 6. Серверный aggregate endpoint по расходам

Сейчас `/expenses` работает по списку расходов. Для финансового раздела этого недостаточно.

Желательно добавить endpoint вида:

`GET /api/v1/reports/expenses-monthly/`

Минимальный состав ответа:

```json
{
  "month": "2026-04",
  "totals": {
    "totalExpenses": "0.00",
    "payrollExpenses": "0.00",
    "advanceExpenses": "0.00",
    "operationalExpenses": "0.00",
    "cashExpenses": "0.00",
    "cashlessExpenses": "0.00"
  },
  "byCategory": [],
  "byEmployee": []
}
```

### Почему это желательно

- фронтенд не будет зависеть от пагинации списка;
- сверка с `cashbox` и `salary-reports` станет серверной, а не клиентской;
- упростится построение отчетов.

---

### 7. Endpoint с доступными месяцами

Сейчас фронтенд строит список доступных месяцев по части appointment-данных. Это не надежный источник.

Желательно добавить endpoint вида:

`GET /api/v1/reports/available-months/`

Пример ответа:

```json
{
  "financial": ["2026-04", "2026-03", "2026-02"],
  "payroll": ["2026-04", "2026-03"],
  "expenses": ["2026-04", "2026-03", "2026-01"]
}
```

---

## Что желательно уточнить в текущих ручках

### `/api/v1/reports/financial-monthly/`

Желательно явно гарантировать:

1. `totals.servicesSum`
2. `totals.productsSum`
3. `totals.discountSum`
4. `totals.debtSum`
5. при необходимости отдельное поле `totals.totalRevenue`

Если `totalRevenue` не планируется, тогда считаем контрактом:

`servicesSum + productsSum = общая выручка`

---

### `/api/v1/reports/payroll-monthly/`

Нужно явно закрепить:

1. что `totals.netSalary` — единственный итог “к выплате”;
2. как учитываются авансы;
3. входят ли удержания в `expensesSum`;
4. должен ли payroll endpoint отдавать дополнительные поля:
   - `advancesSum`
   - `deductionsSum`
   - `payoutsSum`

Это особенно важно для ручной сверки зарплат с расходами.

---

### `/api/v1/cashbox/summary/`

Желательно явно описать:

1. формулу `net`
2. входят ли `paidBalance` и `paidBonuses` в `appointments.totalSum`
3. как считаются безналичные расходы
4. попадают ли зарплаты и авансы в `expenses`
5. по какой дате учитывается операция:
   - дата создания
   - дата учета
   - дата платежа

---

## OpenAPI-расхождения, которые желательно исправить

### Расходы

Сейчас в схемах расходов уже есть `createdAt`, но нет `affectsMonth`, хотя фронтенд уже отправляет его в запросах.

Нужно обновить OpenAPI:

1. `ExpenseCreateRequest`
2. `ExpenseUpdateRequest`
3. `PatchedExpenseUpdateRequest`
4. `ExpenseRead`

И добавить описание:

- `affectsMonth: string | null`
- формат: `YYYY-MM`
- смысл: месяц учета payroll/advance расхода

---

## Критерии приемки

Бэкенд можно считать готовым для полного финансового функционала, если выполняются все условия:

1. Payroll-расходы определяются сервером, а не по названию на фронте.
2. У payroll/advance расходов всегда есть `affectsMonth`.
3. Старые payroll-данные мигрированы.
4. `reports`, `salary-reports`, `cashbox`, `expenses` используют согласованную финансовую семантику.
5. Возвраты/корректировки либо поддержаны, либо явно исключены из текущего бизнес-процесса.
6. OpenAPI соответствует реальному контракту.

---

## Приоритет задач для бэкенда

### P0

1. Ввести серверный признак payroll-расхода
2. Добавить и валидировать `affectsMonth`
3. Сделать миграцию старых payroll-расходов
4. Зафиксировать контракт `reports` vs `cashbox`

### P1

1. Явно определить модель возвратов/корректировок
2. Обновить OpenAPI по расходам
3. Уточнить семантику payroll totals

### P2

1. Добавить aggregate endpoint по расходам
2. Добавить endpoint доступных месяцев

---

## Короткий вывод

Для базовой работы финансовые ручки уже существуют, но для полной консистентности денег бэкенду нужно стать источником истины не только по суммам, но и по финансовой семантике:

- что считается payroll;
- к какому месяцу относится расход;
- как сводятся выручка, расходы и денежный поток;
- как учитывать возвраты и корректировки.

Пока этого нет, фронтенд может показывать цифры, но не может гарантировать безусловную финансовую сходимость во всех сценариях.
