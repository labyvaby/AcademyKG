# Смены сотрудников сохраняются без филиала (employee-schedules.branch = null) — 2026-09-15

**Приоритет: ВЫСОКИЙ.** Экран «Расписание» (`/schedule`) не работает ни на одном филиале.

## Симптом

Администратор добавляет смену врачу и видит «Смена успешно создана», но в календаре
она не появляется. Календарь пустой на всех филиалах.

## Что проверили вживую (Тестовый филиал 2, `593b136e-ba5c-4840-92f7-3e24ab78b0b6`)

1. `POST /api/v1/employee-schedules/`
   ```json
   {
     "employee": "38f94cbe-ca62-4e8d-89cf-1d89c76ff701",
     "date": "2026-09-16",
     "startTime": "09:00:00",
     "endTime": "18:00:00",
     "shiftType": "day",
     "isDayOff": false
   }
   ```
   Ответ **201**, но в ответе `"branch": null`.
   У сотрудника при этом `primaryBranch` = «Тестовый филиал 2».

2. `GET /api/v1/employee-schedules/?branch=593b136e-…` → `count: 0`.
   Эту же смену возвращает только `GET ?employee=38f94cbe-…`.

3. `OPTIONS /api/v1/employee-schedules/` → в `actions.POST` поле `branch` помечено
   `readOnly: true`. Передать филиал с фронта нельзя.

4. `GET /api/v1/employee-schedules/` без фильтра → `count: 39`. **У всех 39 смен
   `branch: null`.**

Фронт (как и для остальных branch-scoped сущностей) добавляет к GET-запросам
`?branch=<активный филиал>`. Поэтому смены без филиала не видны нигде.

## Что просим

1. **При создании смены заполнять `branch`.** Варианты на ваш выбор:
   - из `employee.primaryBranch`;
   - или принимать `branch` в теле POST (снять `readOnly`) — фронт будет слать
     активный филиал;
   - или брать из `?branch=` / контекста запроса.
2. **Миграция данных:** проставить `branch` существующим сменам с `branch = null`
   (по `employee.primaryBranch`).
3. **Фильтр `?branch=`** в `GET /api/v1/employee-schedules/` оставить по полю смены.
   После пп. 1–2 он заработает сам.
4. **Фильтр по датам** в `GET /api/v1/employee-schedules/`: подтвердите имена параметров
   (например `dateFrom` / `dateTo` или `date__gte` / `date__lte`). Сейчас фронт выкачивает
   все смены за всё время постранично и режет месяц на клиенте, при росте данных это
   упрётся в лимиты.
5. **(желательно) Пакетное создание** смен: `POST /api/v1/employee-schedules/bulk/`
   со списком записей. Форма «смены по дням недели на диапазон» сейчас шлёт по одному
   POST на каждый день (до 30+ запросов подряд).

## Открытые вопросы (наши догадки, подтвердите или поправьте)

1. Сотрудник работает в нескольких филиалах (`allowedBranches`). Какой филиал ставить
   смене: `primaryBranch` или тот, в котором её создали? Мы бы предпочли второе
   (принимать `branch` в POST, дефолт — `primaryBranch`).
2. Смены с `branch = null` появились из-за того, что поле добавили позже и не
   мигрировали, или создание никогда не заполняло филиал?
3. Нужен ли `branch` в PATCH (перенос смены в другой филиал), или он неизменяем
   после создания?

## Что сделает фронт после фикса

- Если `branch` станет записываемым — слать активный филиал в POST.
- Перевести загрузку календаря на серверный фильтр по датам месяца.
- Создание диапазона — через bulk (если будет) или последовательно с обходом
  клиентского rate-limit (`skipClientRateLimit`).
