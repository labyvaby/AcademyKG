# Расчётный лист специалиста — реальное время приёмов вместо фиксированной сетки

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25 · эндпоинт `GET /api/v1/reports/specialist-payslip/`

## Проблема

Сейчас `days[].slots[]` — фиксированная сетка 11 часовых слотов `08:00..18:00`,
приём привязывается к слоту по часу начала (`appointmentAt.hour()`). Из-за этого:

- приём в **19:00** (вне окна 08–18) — выпадает из детализации;
- приём в **14:50** (не круглый час) — схлопывается в слот `14:00`, реальное
  время теряется;
- несколько приёмов в один час склеиваются в одну строку.

Заказчик: ребёнок может записаться на любое время (и 19:00, и 14:50), и это
время должно быть видно в таблице расчётного листа как есть.

## Подтверждено живыми данными (Главный, 2026-06, суперадмин GET)

Off-grid времён реально много: 57 приёмов за июнь на :20/:30/:40/:50, есть и вне 08–18
(00:53, 22:18, 23:19). Пример — Канатбекова Мээрим, 2026-06-08, 7 приёмов:
`09:40, 10:20, 11:00, 13:00, 14:30, 15:00, 15:50`. В payslip-сетке:
- времена округлены до часа (09:40→09:00, 14:30→14:00);
- **15:00 и 15:50 схлопнулись в ОДИН слот 15:00** (два ребёнка слиты в одну строку);
- `totals.count=7` сохранён, деньги не теряются — но детализация по времени и по
  детям искажена.
Приёмы вне 08–18 (19:00/20:00/ночные) выпадают из сетки полностью.

**Масштаб потерь — филиал Манас (работает вечерами до 23:30):** 33 оплаченных
ночных приёма (20:00–23:30) за июнь. Сравнение `summary.paidAppointmentsCount`
(истинное) против суммы по сетке `days[].totals.count` по специалистам:
- **Собиров Сардарбек: сетка 103 из 140 → выпало 37 (26%)** — работает вечерами;
- Токтогул уулу Адис: 1; Жорокулов Адилет: 1; остальные топ-специалисты — 0
  (укладываются в 08–18).
Т.е. у вечернего специалиста расчётный лист недосчитывает **четверть** приёмов в
детализации (и, соответственно, начисленное за период в полумесячном PDF). Это не
косметика — лист по нему неверный.

## Что нужно

Перейти от **сетки по часам** к **строке на каждый приём** с его фактическим
временем. То есть `slots[]` — это уже не 11 фиксированных ячеек, а
динамический список фактических приёмов специалиста за день.

### Новый контракт `days[].slots[]`

```ts
days: [
  {
    date: string;            // YYYY-MM-DD (без изменений)
    weekdayLabel: string;    // "Пятница" (без изменений)
    slots: [                 // 0..N элементов — по одному НА КАЖДЫЙ приём специалиста за день
      {
        time: string;             // ФАКТИЧЕСКОЕ время начала, "HH:mm" → "14:50", "19:00"
        patientName: string;      // имя ребёнка (теперь не бывает null — пустых строк-слотов нет)
        lessonType: "individual" | "pair";
        sum: string;              // "Поступила" = paid_cash+card+balance+bonuses (как раньше)
        earned: string;           // доля специалиста (та же payroll-формула, как раньше)
      }
    ],
    totals: {
      count: number;          // = slots.length (кол-во приёмов за день)
      sumTotal: string;       // сумма slot.sum
      sumEarned: string;      // сумма slot.earned
    }
  }
]
```

Изменения по сравнению с текущим контрактом (`backend-request-specialist-payslip.md`):

1. **Сетка убрана.** Больше не «всегда 11 слотов 08:00..18:00». Слотов столько,
   сколько у специалиста было приёмов в этот день.
2. **`time`** = фактическое время начала приёма в формате `HH:mm` (минуты значимы:
   `14:50`, а не `14:00`). По-прежнему TZ Asia/Bishkek.
3. **Приёмы вне 08–18 (07:00, 19:00, 20:00…) теперь ВКЛЮЧАЮТСЯ** в `slots[]`.
   После этого `sum(days[].slots[].earned)` должен сойтись с месячным
   `summary.percentSum` (раньше расходился именно из-за off-grid; см. п. ниже).
4. **Пустых слотов-заглушек больше нет** (`patientName:null`/`lessonType:null`
   уходят). День без приёмов → `slots: []`, `totals.count: 0`.
5. **Один приём = одна строка.** Если в одно время два приёма — две строки, имена
   НЕ склеивать.

### Дни без приёмов — по-прежнему возвращать

`days[]` должен и дальше содержать **все будние дни периода** (`dateFrom..dateTo`),
включая дни, где у специалиста 0 приёмов — но с пустым `slots: []` и
`totals.count: 0`. Фронт по `count == 0` рисует такой день **красной обводкой**
(нерабочий день / нулевой итог — требование заказчика, уже реализовано на фронте).

### Сортировка

`slots[]` — по `time` ASC (теперь с учётом минут).

## Открытые вопросы (требуют решения бэка/заказчика — не закладывать молча)

1. **Семантика `count`/детализации** — включаем ли в строки **неоплаченные**
   приёмы (state выполнен, но `sum=0`/`earned=0`)? Сейчас в сетке неоплаченный
   слот рисовался с `0`. Предлагаю: показывать все **проведённые** приёмы
   специалиста независимо от оплаты (`earned` может быть `0.00`). Подтвердить.
2. **Что считать «приёмом специалиста»** для строки — атрибуция по строке услуги,
   где он исполнитель (как в `slot.sum` сейчас), а не весь appointment. Подтвердить,
   что остаётся та же атрибуция, что и в текущем `slot.sum`/`earned`.
3. **Отменённые / no_show** приёмы — в `slots[]` не показывать (предположение).
4. **Парные/групповые в одно время** — каждая строка услуги отдельной строкой,
   или одна строка на appointment? Предлагаю: по строке услуги специалиста.
5. **Лимит строк на день / вёрстка PDF** — теоретически у специалиста может быть
   >15 приёмов в день, дневная карточка в PDF может переполниться. Это решаем на
   фронте (скролл/перенос), но подтвердите, что ограничения по количеству нет.

## Что НЕ меняется

`summary` (месячный), `period`, `employee`, права (`reports.read`), формулы
`sum`/`earned`, `lessonType`. Меняется только устройство `days[].slots[]`.
