## Q2. Детализация листа не фильтруется по специалисту [ПРИОРИТЕТ: КРИТИЧНЫЙ] — ✅ ЗАКРЫТ и ПРОВЕРЕН на живых данных (2026-06-03)

> Перепроверка после деплоя: 01.05.2026 лист отдаёт `count=7`, `sumTotal=7000`
> (было 90 / 255 600). Кросс-чек `/appointments`: в филиале 90 приёмов, Мирстан
> исполнитель в 7 — совпадает. Детализация теперь фильтруется по специалисту.

### Проблема

В ответе `/specialist-payslip/` блок `days[].slots[]` и `days[].totals`
(колонка «Поступила» = `slot.sum`) содержит **все приёмы филиала**, а не приёмы
конкретного специалиста.

### Воспроизведение (Мирстан, 01.05.2026)

| Метрика в листе | Значение в листе | Факт по специалисту |
|---|---|---|
| `days[].totals.count` за 01.05 | **90** | строк услуг, где исполнитель Мирстан — **7** (все СМК) |
| `days[].totals.sumTotal` за 01.05 | **255 600** | реальная выручка Мирстана за день ≈ 7 000 (7×1000) |

Контрольная сверка через `GET /api/v1/appointments/?date=2026-05-01&branch=...`:
- всего приёмов в филиале за день — ровно **90**;
- суммарный paid (`paidCash+paidCard+paidBalance+paidBonuses`) — ровно **255 600**.

Совпадение точное → лист отдаёт филиал целиком. Слот листа = сумма всех приёмов
филиала в этот час (напр. слот `08:00` = 24 000 = приёмы филиала в 08:00 (14 000) +
08:30 (10 000)).

### Важная подсказка: summary считается ПРАВИЛЬНО

`summary` фильтрован по специалисту корректно:
`grossEarnings=78000`, `paidAppointmentsCount=156` = ровно `500 × 156`.
За май у Мирстана 161 приём (158 paid), 159 строк СМК — сходится.

Значит баг **только в построении `days[]`**, а не в агрегации `summary`. Это два
разных пути в коде — чинить именно билдер дневной детализации, summary не трогать.

### Что нужно

В `days[].slots[]`, `days[].totals` и «Поступила» учитывать **только приёмы/услуги,
где этот специалист — исполнитель** (`services[].performer == employee`). Сейчас,
судя по всему, queryset детализации не фильтруется по `employee`.

## Q3. По какой сущности атрибутировать специалисту: приём или строка услуги? [ПРИОРИТЕТ: ВЫСОКИЙ]

### Вопрос

В приёме может быть несколько услуг с разными исполнителями (`services[].performer`).
После фикса Q2 нужно зафиксировать формулу:

- «Поступила» (`slot.sum`) и счётчик занятий считаются по **строке услуги**
  конкретного специалиста (его `price` / его доля оплаты), а не по `total`
  всего приёма?
- Как делится частичная оплата приёма между несколькими услугами/исполнителями?

Это нужно, чтобы «Поступила» и `earned` не задваивались, когда в одном приёме
работают двое.

## Q4. Фикс-ставочники в дневном листе [ПРИОРИТЕТ: СРЕДНИЙ] — ✅ ЗАКРЫТ бэком (commit `f0695d7`)

> **Ответ бэка (2026-06-03):** `slot.earned` теперь = `dynamic_service_earning +
> fixed_appointment_earning`, где `fixed_appointment_earning = fixed_per_appointment ×
> payment_factor`. Фикс-ставка считается **один раз на приём** (несколько услуг в одном
> приёме фикс не задваивают). Изменились только `days[].slots[].earned` и
> `days[].totals.sumEarned`; структура и остальные поля прежние. Фронт уже рендерит
> `slot.earned` / `sumEarned` → правок не требуется, фикс подхватится после деплоя.
> Осталось: QA на живых данных (Мирстан, фикс 500/приём).

### Проблема

Для специалиста на фиксированной ставке (per-appointment / per-hour;
`fixed_salary.enabled=true`, `percent=0`) в `days[].slots[]` поле `earned=0`
по всем слотам. Заработок (напр. 500/приём) попадает только в месячный
`summary.grossEarnings`, потому что формула слота
`earned = service_price × paymentFactor × percent` при `percent=0` даёт ноль.

Итог: в дневной детализации заработок фикс-ставочника **не виден вообще**.

### Вопрос

Что показывать в колонке «начислено» для фикс-ставочников:
- ставку за приём/час прямо в слоте (напр. 500 × число приёмов в слоте), или
- для них отдельная форма листа без поколоночного «начислено»?

Связано с вопросом созвона «как включать/показывать окладников».

## Q5. Логотип и бренд на уровне филиала [ПРИОРИТЕТ: СРЕДНИЙ]

### Проблема

На печатных формах бренд сейчас захардкожен на фронте и одинаков для всех филиалов:
- `src/utility/pdfGenerator.ts` — текст справки «...в «Academy KG»»;
- `src/components/ui/PaymentReceipt.tsx` — дефолт `orgName = "Аутизм победим KG"`.

Нужно, чтобы у каждого филиала был **свой логотип и бренд** (напр. «Аутизм Победим
Манас» vs «Главный филиал»).

Текущая модель не позволяет: объект `branch` отдаёт только
`{ id, organization, organizationName, name, address, createdAt }` — **поля логотипа
нет ни у филиала, ни у организации**.

### Что нужно от бэкенда

Добавить в схему `Branch` поле с логотипом (и, при необходимости, отдельное
отображаемое имя бренда):

```yaml
Branch:
  properties:
    logoUrl:
      type: string
      format: uri
      nullable: true
      readOnly: true
    brandName:        # опционально; если нет — фронт берёт name
      type: string
      nullable: true
```

Плюс способ загрузить/обновить логотип филиала (`PATCH /api/v1/branches/{id}/`
с multipart, либо отдельный эндпоинт).

### Что делает фронт после этого

- Текст бренда — уже сейчас можно брать из `branch.name` (бренд = филиал).
- Картинку логотипа — `<img src={branch.logoUrl}>` в шапке расчётного листа,
  чека (`PaymentReceipt`) и справки (`pdfGenerator`), вместо хардкода.
