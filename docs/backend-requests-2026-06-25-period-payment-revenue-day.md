# Оплата за период: вся выручка на день оплаты, а не размазана по дням приёмов

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25

## Требование заказчика

При оплате «за срок» (запись приёма на период — несколько сессий на разные дни)
вся оплаченная сумма должна признаваться в кассе/отчётах **в день оплаты одним
числом**, а не распределяться по дням, на которые стоят приёмы.

Сейчас: «оплата идёт по другим дням» — клиент заплатил всю сумму сегодня, а в
отчётах она появляется частями в дни будущих/прошлых сессий.

## Как сейчас устроено (фронт)

Запись «на период» (`HomeAddAppointmentDrawer`, режим «На период»):
1. создаёт **N приёмов — по одному на каждую дату** периода (один приём = одна
   сессия на своём `appointmentAt`);
2. предлагает оплату за весь период (`PaymentSidebar`, bulk-режим) — сумма
   **делится поровну между всеми N приёмами** (`distributeAmount`) и каждый приём
   PATCH-ится своей долей:
   ```
   PATCH /api/v1/appointments/{id}/  { paidCash: share, paidCard: share, discount: share, ... }
   ```

Так как `paid_*` лежат на каждом приёме, а приёмы стоят на разных датах,
отчёты (`financial-monthly`, `cashbox/summary`, `daily-summary`) разносят выручку
**по дате приёма** → сумма размазывается по дням срока. Это и есть жалоба.

## Что нужно

Признавать оплату за период **в день фактической оплаты** (TZ Asia/Bishkek),
одной суммой в кассе/выручке, при этом:
- приёмы периода остаются **оплаченными** (без долга);
- это должно сходиться в `cashbox/summary`, `financial-monthly` (`days[]`/`totals`),
  `daily-summary` (`income`, наличка).

Похоже на модель абонемента из `docs/subscription-service-spec.md` (покупка =
одна продажа в день оплаты; сессии покрыты).

## Открытые вопросы (нужно решение бэка — не закладывать молча)

1. **Механизм даты.** Как бэк свяжет выручку с днём оплаты?
   - (а) добавить дату/таймстамп оплаты на приём (`paidAt`) и в кассовых/выручка-
     отчётах бакетировать по `paidAt`, а не по `appointmentAt`; либо
   - (б) отдельная сущность «оплата за период» (one payment → N appointments),
     дата = день оплаты, отчёты берут выручку из неё.
   Какой вариант предпочтителен в текущей модели данных?
2. **Сигнал от фронта.** Что фронт должен прислать, чтобы бэк понял «это оплата за
   период единой суммой в день оплаты»? Варианты: флаг на PATCH
   (`paymentScope: "period_single_day"`), отдельный эндпоинт
   `POST /period-payments/`, или группа `periodGroupId` на приёмах. Дайте контракт —
   фронт перепишет `handleSaveBulk` под него.
3. **Заработок специалиста — НЕ переносить.** Доля специалиста за сессию (`earned`
   в payslip/`payroll-monthly`) считается из оплаты по приёму и должна оставаться
   **на дне сессии** (специалист отработал в тот день), даже если ВЫРУЧКА/касса
   признаётся в день оплаты. Подтвердите, что выручка (касса) и начисление ЗП
   расходятся по датам: касса → день оплаты, earned специалиста → день сессии.
   Если это ломает текущую формулу — нужно явное решение.
4. **Какие отчёты затронуты.** Ожидаем: `cashbox/summary` (нал/безнал по дню
   оплаты), `financial-monthly` (`days[].cashSum/cardSum/servicesSum` на день
   оплаты), `daily-summary` (наличка/приход). Уточните, попадает ли сюда `debtSum`
   (долг должен быть 0 у покрытых приёмов).
5. **Частичная оплата периода / возврат.** Если оплатили не весь период или
   отменили часть сессий — как пересчитывается выручка дня оплаты? (предложение:
   на старте поддержать только полную оплату периода, частичную — позже).
6. **«День оплаты»** = серверное время приёма платежа в Asia/Bishkek. Подтвердить.
