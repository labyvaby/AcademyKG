# Сводка дня не видит оплаты за период: касса дня оплаты пустая, приход размазан по дням сессий

## Симптом (жалоба заказчика, проверено вживую)

Оплата за период через новый `POST /api/v1/period-payments/` (контракт
2026-06-26) в **«Сводке дня»** (`GET /api/v1/reports/daily-summary/`) работает
«как раньше»:

- в день оплаты сумма периода **не появляется вообще** — ни в `day.income.cash`,
  ни в `day.income.accruedTotal`;
- «приход» (`accruedTotal`) **размазан по датам сессий** — каждая дата периода
  показывает свою долю.

При этом `financial-monthly` и `cashbox/summary` работают **правильно**
(проверено вживую: financial-monthly — вся сумма в `days[].cashSum`/`servicesSum`
дня оплаты; cashbox/summary с `dateFrom=dateTo=день оплаты` — сумма в
`appointments.cashSum`, дни сессий — 0). То есть из тикета 2026-06-25 починено
всё, **кроме** `daily-summary` — а он там был перечислен в затронутых
(«это должно сходиться в … `daily-summary` (`income`, наличка)»).
`daily-summary` — единственное оставшееся место, где сумма периода размазана
по дням сессий и отсутствует в дне оплаты; заказчик смотрит именно этот отчёт.

## Что нужно

`daily-summary` должен учитывать period-payments так же, как financial-monthly:

1. **День оплаты (`paidAt`, Asia/Bishkek):** сумма периода целиком в
   `day.income` (cash/cashless/balance/bonuses по способам оплаты periodPayment)
   и в `day.income.accruedTotal`. В репро: 02.07 → `income.cash=3000`,
   `accruedTotal=4000`.
2. **Дни сессий:** приёмы, покрытые periodPayment, **не** дают вклада в
   `income`/`accruedTotal` своих дат (10–12.07 → без долей по 1000).
3. **`cashPosition.actualCash`** дня оплаты должен включать наличную часть
   periodPayment — заказчик сверяет по этому полю фактическую кассу дня.
4. Возврат (`POST /period-payments/{id}/refund/`) — зеркально: минус из дня
   оплаты (или дня возврата — см. вопрос 3), сессии снова с долгом.

Заработок специалиста (`earned` в payslip/payroll) НЕ трогать — остаётся на дне
сессии, как зафиксировано в контракте 2026-06-26.

## Требование 2 (заказчик 2026-07-02): список period-payments за день — для «Регистратуры»

Заказчик: «в регистратуре должен быть итог за всю оплату в день оплаты» —
на странице дня (Регистратура) в день покупки нужно показать оплаты за период
этого дня общей суммой (и, желательно, списком: клиент — сумма — период).

Сейчас фронту неоткуда взять эти данные (проверено вживую):
- `GET /api/v1/period-payments/` → **405** (эндпоинт POST-only, списка нет);
- на приёме (list и detail) **нет ссылки** на periodPayment и нет paidAt —
  восстановить «оплаты дня» по приёмам невозможно.

**Просим эндпоинт списка**, предложение:

```
GET /api/v1/period-payments/?paidDate=YYYY-MM-DD&branch=<uuid>
→ 200 { data: { results: [{
    id, paidAt, patient: {id, fullName},
    paidCash, paidCard, paidBalance, paidBonuses, discount, totalAmount,
    appointmentsCount, periodFrom, periodTo   // либо appointments: [{id, appointmentAt}]
}] } }
```

- `paidDate` — день по Asia/Bishkek (как в остальных отчётах).
- Права: логично `appointments.read` (страница Регистратуры) — подтвердите.
- Если удобнее, альтернатива: блок `periodPayments[]` в существующем
  дневном ендпоинте — скажите контракт, фронт подстроится.

## Открытые вопросы (нужно решение бэка — не закладывать молча)

1. **`byKind`/`byCategory` в день оплаты.** Куда отнести 3000 в
   `income.byKind` (group/individual) и `byCategory` (afk/lfk/…)? Ожидаем — по
   услугам покрытых приёмов (сумма их долей), но подтвердите.
2. **`counts.appointmentsCount` дня оплаты.** Приёмы периода стоят на других
   датах — счётчики дня оплаты, видимо, не меняются (меняется только доход)?
3. **Возврат.** Минус в день первоначальной оплаты (пересчёт истории) или в
   день возврата (новая операция)? Для кассы логичнее день возврата.
4. **`monthToDate`.** Если оплата и сессии в одном месяце — суммарно сойдётся,
   но если период пересекает границу месяца, monthToDate должен считать по
   дню оплаты (как financial-monthly `totals`).
