# Запросы к бэкенду — «Сводка дня» (2026-06-04)

> ✅ **ЗАКРЫТО (2026-06-04):** бэк реализовал единый ендпоинт
> `GET /api/v1/reports/daily-summary/?branch&date&responsibleEmployee` — покрывает все
> Q1–Q5 ниже (разбивка `byCategory`/`byKind`, счётчики вкл. `uniquePatientsCount`,
> `individualSpecialistsCount`, `lfkRecalculationCount`, `previousDayCashNet`, готовая
> `actualCash`). Спец бэка: `frontend-daily-summary-api.md`. Вопросы Q1–Q5 оставлены
> для истории. Категории услуг (`reporting_category`) админ проставляет вручную через Service API.

Фича фронта: PDF-генератор **«Сводка дня»** — дневная финансовая сводка с накоплением
от 1-го числа месяца до выбранного дня. Образец-фото:
`photo_2026-05-20_17-34-15.jpg` (значения на 19.05.2026).

Пользователь выбирает **любой день** (date picker). Все строки «итого / с 01» —
накопление от 1-го числа месяца выбранного дня **до выбранного дня** (не до конца месяца).

## Что УЖЕ покрыто текущим API (бэку делать НЕ нужно)

Эти строки фронт соберёт сам из существующих ендпоинтов:

| Строка отчёта | Источник |
|---|---|
| Приход (общий, наличка/безнал) | `GET /api/v1/cashbox/summary/?branch&dateFrom&dateTo` → `appointments`, `net` |
| Итого наличка за день / 01–день | `cashbox/summary` `net.cashSum` (диапазон `dateFrom=dateTo=день` и `dateFrom=01&dateTo=день`) |
| Кол-во занятий | `cashbox/summary` → `counts.appointmentsCount` |
| Итого расходы (операционные) за день / период | `GET /api/v1/reports/expenses-monthly/` → `totals.operationalExpenses`, `byDate[]` |
| Авансы | `expenses-monthly` → `totals.advanceExpenses` (или `payroll-transactions`) |
| Штрафы (= удержания за опоздания) | `expenses-monthly` → `totals.deductionExpenses` |
| Расходы конкретного человека | `expenses-monthly` → `byEmployee[]` (по `employeeId`) |
| Долги детей за день / период | `GET /api/v1/reports/financial-monthly/` → `days[].debtSum` |
| Фактическая наличка | формула на фронте: `наличка(01–день) − авансы(итого) − долги детей(итого) − расходы человека(итого)` (сверено: 1172653−129890−53800−0 = 988963 ✓) |

## Чего НЕТ в API — нужны доработки

### Q1. Разбивка прихода: АФК (групповые) / индивидуальные / Иглотерапия [ПРИОРИТЕТ: ВЫСОКИЙ]

`cashbox/summary` даёт общий `appointments.totalSum`, но **не делит по типу занятия / категории услуги**.
В отчёте приход разнесён на три отдельные строки:
- **Приход АФК** — выручка по ГРУППОВЫМ тренировкам (АФК), показывается как исключение.
- **Приход** — общая выручка БЕЗ АФК (все индивидуальные занятия).
- **Иглотерапия** — отдельная категория услуги (врач из другой поликлиники).

**Запрос:** можно ли расширить `cashbox/summary` разбивкой выручки по группам/категориям —
например `appointments.byKind: { group, individual }` и/или `appointments.byServiceCategory[]`?
Либо отдельный лёгкий ендпоинт «приход по категориям за диапазон».

> Фронт-обходной путь (если бэк не успевает): считать из `appointments-aggregated`
> по `group != null` и категории услуги — но это тяжелее и зависит от консистентности данных.

### Q2. Счётчики оплат АФК / ЛФК + «перерасчёт» [ПРИОРИТЕТ: ВЫСОКИЙ]

В отчёте:
- **Оплата за АФК на сегодня** = 1 — это **количество оплат** (шт) по АФК за день, не сумма.
- **Оплата за ЛФК общая количество** = 53 (**0 перерасчет**) — количество оплат ЛФК до выбранного дня
  + поле **«перерасчёт»** = число перерасчётов (делают ребёнку при чём-то серьёзном).

В текущем API таких счётчиков нет, особенно понятия **«перерасчёт»**.

**Запрос:** добавить за диапазон счётчики:
- `afkPaymentsCount` (оплат АФК),
- `lfkPaymentsCount` (оплат ЛФК),
- `lfkRecalcCount` («перерасчёт»).

Уточнение к бэку: что технически считается «оплатой АФК/ЛФК» (по категории услуги? по типу приёма?)
и как помечается «перерасчёт» в данных?

### Q3. Количество специалистов по индивидуальным занятиям [ПРИОРИТЕТ: СРЕДНИЙ]

**Количество специалистов** = 9 (чел), до выбранного дня, **только специалисты по индивидуальным
занятиям**. Двигательные, админы и т.п. НЕ входят. Готового счётчика в API нет.

**Запрос:** отдать `specialistsCount` (distinct сотрудников-исполнителей по индив-приёмам за диапазон).
Либо подтвердить, что фронт может посчитать это сам (distinct `doctor` по индив-приёмам) —
тогда нужен признак «индивидуальное занятие» в `appointments-aggregated`.

### Q4. «Наличка за прошлый день» — baseline накопления [ПРИОРИТЕТ: СРЕДНИЙ]

**Наличка за прошлый день** = 1103753 — накопленный остаток налички на конец предыдущего дня.
Фронт может взять `cashbox/summary net.cashSum` за `[старт..день−1]`, НО непонятна **стартовая дата
накопления остатка кассы** (с начала месяца? с момента открытия кассы? сквозной остаток за всё время?).

**Вопрос:** от какой даты считается остаток налички? Если это сквозной «остаток в кассе» —
есть ли ендпоинт/поле текущего остатка кассы, или его всегда вычислять от фиксированной точки?

---

### Q5. Уникальные дети vs посещения [ПРИОРИТЕТ: НИЗКИЙ]

**Общее количество детей с 01–день** = 906. Если это **уникальные дети**, в API такого поля нет
(`financial-monthly` отдаёт только `appointmentsCount` = посещения).

**Вопрос:** 906 — это уникальные дети или сумма посещений?
- Если посещения — закрыто (`appointmentsCount`).
- Если уникальные — нужен `uniquePatientsCount` за диапазон.

## Общие замечания

- Все диапазоны — `dateFrom` = 1-е число месяца выбранного дня, `dateTo` = выбранный день.
- Желательно, чтобы новые счётчики (Q2–Q5) тоже принимали `branch` + `dateFrom`/`dateTo`,
  как `cashbox/summary`, — чтобы фронт собирал «за день» и «01–день» одним стилем запросов.
- Идеальный вариант для фронта: **один агрегирующий ендпоинт** `GET /api/v1/reports/daily-summary/?branch&date`,
  который вернёт сразу все поля отчёта (приход с разбивкой, наличка, расходы, авансы, долги,
  штрафы, счётчики). Но это по желанию бэка — фронт справится и точечными запросами из таблицы выше + Q1–Q5.
