# Вопросы к бэкенду — «Сводка дня», follow-up после ревизии (2026-06-11)

Контекст: фронт-ревизия фичи «Сводка дня» (`GET /api/v1/reports/daily-summary/`,
спека бэка `frontend-daily-summary-api.md`, исходное ТЗ
`docs/backend-requests-daily-summary.md`). Фронт-баги починены отдельно; ниже —
несоответствия семантики, которые фронт исправить не может. Просьба ответить
по каждому пункту (или подтвердить, что текущее поведение — осознанное решение).

> **Важно (2026-06-11):** фото-образец заказчика (19.05.2026) даёт точные
> уравнения, и `cashPosition` им противоречит (см. F3). Фронт временно перестал
> использовать `cashPosition` и считает кассовые строки сам из `day`/`monthToDate`:
> `наличка = income.total`, `прошлый день = mtd − day`,
> `фактическая = mtd.income.total − mtd.advances − mtd.debt − mtd.respExpenses`.
> После согласования формул вернёмся на готовые поля.

## F1. `afkPaymentsCount` / `lfkPaymentsCount` — приёмы или оплаты? [ВЫСОКИЙ]

Исходный запрос (Q2): «**количество оплат** по АФК/ЛФК». В спеке ответ описан как
«**Приёмов с АФК/ЛФК-услугами**» — про оплаченность ни слова.

**Вопрос:** входит ли в счётчик приём с АФК/ЛФК-услугой, по которому ещё не было
оплаты (scheduled/arrived, paid_* = 0)? Если да — счётчик показывает посещения,
а не оплаты, и строки отчёта «Оплата за АФК на сегодня» / «Оплата за ЛФК общая»
будут завышены. Ожидание заказчика: считать только приёмы с фактической оплатой
(paid_cash + paid_card + paid_balance + paid_bonuses > 0) за диапазон.

## F2. `previousDayCashNet` — baseline с начала месяца [НИЗКИЙ, ослаблен]

Исходный вопрос Q4 («от какой даты копится остаток налички?») де-факто закрыт
выбором бэка: накопление с 1-го числа месяца, в первый день месяца
`previousDayCashNet = 0`.

Фото-образец согласуется с месячным baseline: 1 103 753 на утро 19-го дня —
правдоподобное накопление при ~65 тыс./день. Считаем месячную модель принятой;
если заказчик когда-нибудь попросит сквозной остаток кассы — вернёмся.

## F3. `netCash`/`actualCash` противоречат фото-образцу: двойное вычитание авансов [ВЫСОКИЙ, доказано]

Фото 19.05.2026 даёт точные уравнения заказчика:

```
5000 + 55400 + 8500            = 68900      «наличка за сегодня» = весь приход дня
1103753 + 68900                = 1172653    прошлый день + сегодня = период
1172653 − 129890 − 53800 − 0   = 988963     фактическая = период − авансы − долги − расходы отв.
```

В день отчёта выдано 20 000 аванса, но «наличка за сегодня» = 68 900 (полный
приход), а не 48 900 → **авансы из «налички» не вычитаются**; они вычитаются
ровно один раз — в фактической наличке. Выплат ЗП в модели образца нет вообще.

Формулы спеки этому противоречат:

```
netCash    = cash_income − operational − advance − payroll     ← авансы вычтены здесь...
actualCash = monthToDateCashNet − advance − debt − respExpenses ← ...и ещё раз здесь
```

Плюс `netCash` берёт только наличный канал (`cash_income`), а строки прихода
образца — `income.total` (все каналы): инвариант «приход = наличка за сегодня»
на `cashPosition` не сходится в принципе.

**Просьба:** привести `cashPosition` к модели образца:
`*CashNet = income.total` за диапазон (без вычетов),
`actualCash = mtdTotal − mtdAdvances − mtdDebt − respExpenses`.
Фронт пока считает это сам (см. шапку), после фикса вернётся на готовые поля.

Открытым остаётся: вычитать ли операционные расходы из «налички» (на фото
день с нулевыми расходами — не проверить; из формулы фактической они выпадают).
Вопрос задан заказчику, ответ передадим.

## F4. Долги в фактической наличке и природа «прихода» [СРЕДНИЙ]

Вычитание долгов фото подтверждает (уравнение фактической налички). Но оно
осмысленно, только если «приход» — **начисленная** стоимость оказанных услуг
(тогда «минус долг» даёт реально полученные деньги). Бэк же считает `income`
по фактическим `paid_*` — из фактически полученного вычитать долг второй раз
неверно. На фото день с нулевым долгом — не проверить.

**Вопрос (задан и заказчику):** строки прихода — это полученные деньги или
стоимость проведённых занятий? Если начисление — `income` для сводки надо
считать от `total_amount` приёмов, а не от `paid_*`.

Разбивка «АФК / Иглотерапия / Приход» работает только когда админ проставил
`reportingCategory` услугам (PATCH `/api/v1/services/{id}/`). Пока всё в `other`:
строки АФК/иглотерапии — нули, «Приход» — вся выручка. На чьей стороне
прогон по существующим услугам — админ заказчика или скрипт бэка?
