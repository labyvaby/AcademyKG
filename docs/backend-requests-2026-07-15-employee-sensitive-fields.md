# Кассир со всеми правами не может создать сотрудника (sensitive-поля) — 2026-07-15

## Симптом

Заказчик выдал роли **cashier** все права через «Роли и права» (мы проверили вживую:
`GET /api/v1/roles/72e50bcf-b180-4a77-9efb-78a2dfb1cd8b/` возвращает **все 101 permission**,
включая `employees.create/read/update/delete`, `users.create`, `app_settings.update`).

Тем не менее сотрудник «Кассир Фергана» (Файзиев Дониёрбек, филиал «АП Фергана»,
employee `ba24e1f8-e4b2-4080-8c98-5b78334eff54`) при создании сотрудника получает **403**:

```
insufficient permissions to modify sensitive employees fields
```

Запрос фронта — обычный `POST /api/v1/employees/`:

```json
{
  "fullName": "…",
  "role": "<uuid роли>",
  "status": "active",
  "organization": "<uuid организации>",
  "branch": "<uuid филиала>",
  "userPhoneNumber": "+996…"
}
```

## Почему это тупик для фронта

- Поскольку у роли есть **все** зарегистрированные permissions, проверка «sensitive-полей»
  на бэке очевидно завязана **не на permission**, а на роль (superadmin?) или `is_superuser`.
  Значит выдать «правильное право» через «Роли и права» невозможно в принципе.
- При **редактировании** фронт уже умеет не отправлять sensitive-поля (`role`, `status`,
  `organization`, `branch`) для непривилегированных пользователей. Но при **создании**
  сотрудника без `role` и `branch` не обойтись — форма без них не имеет смысла.

## Что просим

1. **Сказать точное правило**: какие поля бэк считает sensitive и какое условие
   (роль? флаг? permission?) даёт право их записывать. Мы синхронизируем фронт-гейты
   с этим правилом (сейчас фронт использует `app_settings.update` как приближение —
   судя по 403, оно неверное).
2. **Перевести проверку на permission**, чтобы ею можно было управлять из «Ролей и прав».
   Предлагаемые варианты (на ваш выбор):
   - использовать уже существующие `employees.create` / `employees.update` — раз право
     на создание сотрудника выдано, назначение роли/филиала при создании логично разрешить;
   - либо завести отдельное право вида `employees.manage_sensitive` и добавить его
     в реестр `GET /api/v1/permissions/` — тогда заказчик сам решает, кому это можно.
3. Пока правка не выехала — подтвердите, что **обходного пути нет** (например,
   `POST /employees/` без sensitive-полей + отдельный endpoint для назначения роли).
