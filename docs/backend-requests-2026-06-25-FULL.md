# Расчётный лист специалиста — реальное время приёмов вместо фиксированной сетки

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25 · эндпоинт `GET /api/v1/reports/specialist-payslip/`

## Проблема

Сейчас `days[].slots[]` — фиксированная сетка 11 часовых слотов `08:00..18:00`,
приём привязывается к слоту по часу начала (`appointmentAt.hour()`). Из-за этого:

- приём в **19:00** (вне окна 08–18) — выпадает из детализации;
- приём в **14:50** (не круглый час) — схлопывается в слот `14:00`, реальное
  время теряется;
- несколько приёмов в один час склеиваются в одну строку.

Заказчик: ребёнок может записаться на любое время (и 19:00, и 14:50), и это
время должно быть видно в таблице расчётного листа как есть.

## Подтверждено живыми данными (Главный, 2026-06, суперадмин GET)

Off-grid времён реально много: 57 приёмов за июнь на :20/:30/:40/:50, есть и вне 08–18
(00:53, 22:18, 23:19). Пример — Канатбекова Мээрим, 2026-06-08, 7 приёмов:
`09:40, 10:20, 11:00, 13:00, 14:30, 15:00, 15:50`. В payslip-сетке:
- времена округлены до часа (09:40→09:00, 14:30→14:00);
- **15:00 и 15:50 схлопнулись в ОДИН слот 15:00** (два ребёнка слиты в одну строку);
- `totals.count=7` сохранён, деньги не теряются — но детализация по времени и по
  детям искажена.
Приёмы вне 08–18 (19:00/20:00/ночные) выпадают из сетки полностью.

**Масштаб потерь — филиал Манас (работает вечерами до 23:30):** 33 оплаченных
ночных приёма (20:00–23:30) за июнь. Сравнение `summary.paidAppointmentsCount`
(истинное) против суммы по сетке `days[].totals.count` по специалистам:
- **Собиров Сардарбек: сетка 103 из 140 → выпало 37 (26%)** — работает вечерами;
- Токтогул уулу Адис: 1; Жорокулов Адилет: 1; остальные топ-специалисты — 0
  (укладываются в 08–18).
Т.е. у вечернего специалиста расчётный лист недосчитывает **четверть** приёмов в
детализации (и, соответственно, начисленное за период в полумесячном PDF). Это не
косметика — лист по нему неверный.

## Что нужно

Перейти от **сетки по часам** к **строке на каждый приём** с его фактическим
временем. То есть `slots[]` — это уже не 11 фиксированных ячеек, а
динамический список фактических приёмов специалиста за день.

### Новый контракт `days[].slots[]`

```ts
days: [
  {
    date: string;            // YYYY-MM-DD (без изменений)
    weekdayLabel: string;    // "Пятница" (без изменений)
    slots: [                 // 0..N элементов — по одному НА КАЖДЫЙ приём специалиста за день
      {
        time: string;             // ФАКТИЧЕСКОЕ время начала, "HH:mm" → "14:50", "19:00"
        patientName: string;      // имя ребёнка (теперь не бывает null — пустых строк-слотов нет)
        lessonType: "individual" | "pair";
        sum: string;              // "Поступила" = paid_cash+card+balance+bonuses (как раньше)
        earned: string;           // доля специалиста (та же payroll-формула, как раньше)
      }
    ],
    totals: {
      count: number;          // = slots.length (кол-во приёмов за день)
      sumTotal: string;       // сумма slot.sum
      sumEarned: string;      // сумма slot.earned
    }
  }
]
```

Изменения по сравнению с текущим контрактом (`backend-request-specialist-payslip.md`):

1. **Сетка убрана.** Больше не «всегда 11 слотов 08:00..18:00». Слотов столько,
   сколько у специалиста было приёмов в этот день.
2. **`time`** = фактическое время начала приёма в формате `HH:mm` (минуты значимы:
   `14:50`, а не `14:00`). По-прежнему TZ Asia/Bishkek.
3. **Приёмы вне 08–18 (07:00, 19:00, 20:00…) теперь ВКЛЮЧАЮТСЯ** в `slots[]`.
   После этого `sum(days[].slots[].earned)` должен сойтись с месячным
   `summary.percentSum` (раньше расходился именно из-за off-grid; см. п. ниже).
4. **Пустых слотов-заглушек больше нет** (`patientName:null`/`lessonType:null`
   уходят). День без приёмов → `slots: []`, `totals.count: 0`.
5. **Один приём = одна строка.** Если в одно время два приёма — две строки, имена
   НЕ склеивать.

### Дни без приёмов — по-прежнему возвращать

`days[]` должен и дальше содержать **все будние дни периода** (`dateFrom..dateTo`),
включая дни, где у специалиста 0 приёмов — но с пустым `slots: []` и
`totals.count: 0`. Фронт по `count == 0` рисует такой день **красной обводкой**
(нерабочий день / нулевой итог — требование заказчика, уже реализовано на фронте).

### Сортировка

`slots[]` — по `time` ASC (теперь с учётом минут).

## Влияние на фронт

- `src/utility/specialistPayslipPdf.ts` уже рендерит `slot.time` как есть и
  не завязан на 11 строк — динамическое число строк отрисуется без правок.
  Красная обводка дня при `totals.count === 0` уже добавлена.
- `src/types/reports.ts` — снимем комментарии про «фиксированную сетку 11 слотов»
  и `patientName: null` после подтверждения контракта.

## Открытые вопросы (требуют решения бэка/заказчика — не закладывать молча)

1. **Семантика `count`/детализации** — включаем ли в строки **неоплаченные**
   приёмы (state выполнен, но `sum=0`/`earned=0`)? Сейчас в сетке неоплаченный
   слот рисовался с `0`. Предлагаю: показывать все **проведённые** приёмы
   специалиста независимо от оплаты (`earned` может быть `0.00`). Подтвердить.
2. **Что считать «приёмом специалиста»** для строки — атрибуция по строке услуги,
   где он исполнитель (как в `slot.sum` сейчас), а не весь appointment. Подтвердить,
   что остаётся та же атрибуция, что и в текущем `slot.sum`/`earned`.
3. **Отменённые / no_show** приёмы — в `slots[]` не показывать (предположение).
4. **Парные/групповые в одно время** — каждая строка услуги отдельной строкой,
   или одна строка на appointment? Предлагаю: по строке услуги специалиста.
5. **Лимит строк на день / вёрстка PDF** — теоретически у специалиста может быть
   >15 приёмов в день, дневная карточка в PDF может переполниться. Это решаем на
   фронте (скролл/перенос), но подтвердите, что ограничения по количеству нет.

## Что НЕ меняется

`summary` (месячный), `period`, `employee`, права (`reports.read`), формулы
`sum`/`earned`, `lessonType`. Меняется только устройство `days[].slots[]`.

# «Занятия за день»: скидочные занятия не попадают в таблицу

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25 · эндпоинт `GET /api/v1/reports/daily-lessons/`

## Симптом (заказчик)

В таблице «Занятия» дневного отчёта **не фиксируются скидочные занятия** —
по услугам дефектология, логопед-дефектолог, массаж общий детский и др. Занятия,
проведённые со скидкой/по особой цене, должны идти **белой строкой-исключением**
(`category.exceptions[]`), но не появляются.

## Фронт проверен — он корректен

Фронт рендерит **все** `categories[].exceptions[]` как белые строки
(`services/dailyLessons.ts` → `utility/dailyLessonsPdf.ts`, без фильтра). Значит
скидочные занятия **не приходят в ответе**. Корень — на бэке.

## ПОДТВЕРЖДЕНО на живых данных (Главный филиал, 2026-06-22, суперадмин GET)

В этот день в филиале было **3 скидочных приёма** (частичная скидка, оплачены):
```
СМК           total=1000  discount=400  paid=600  status=paid  perf=Аскаров Тамирлан
СМК           total=1000  discount=400  paid=600  status=paid  perf=Байматов Нурлан
Дефектология  total=1000  discount=400  paid=600  status=paid  perf=Койбагарова Гульзат
```
Ответ `GET /reports/daily-lessons/?branch=<Главный>&date=2026-06-22`:
```
CAT "Дефектология" std{count:12, unitPrice:1000, total:12000} exceptions:[]
CAT "Логопед"      std{count:5,  unitPrice:800,  total:4000}  exceptions:[]
CAT "Логопед час"  std{count:3,  unitPrice:1000, total:3000}  exceptions:[]
CAT "СИ"           std{count:11, unitPrice:800,  total:8800}  exceptions:[]
CAT "СМК"          std{count:28, unitPrice:1000, total:28000} exceptions:[]
lessons.totals: { count:59, total:55800 }
```
**Exceptions пусты во ВСЕХ категориях.** Скидочные занятия попали в **синий
`standard`** и посчитаны по **номинальной** цене: СМК 28×1000 (2 скидочных учтены
как 1000, а не 600), Дефектология 12×1000 (1 скидочное как 1000). Итог `total=55800`
**завышен** на 3×400 = 1200 (фактически оплачено 54600).

## Причина (подтверждена) — классификация по номинальной цене, а не по фактической

Бэк делит «стандарт vs исключение» по номинальной цене `SellableItem` (priceSom).
Скидочное занятие имеет **ту же** номинальную цену → уходит в синий агрегат,
отдельной белой строки нет, а его выручка считается по номиналу (1000), а не по
факту (600).

**Нужно:** «исключение» определять по **фактической цене занятия за вычетом
скидки** (effective = `total_amount − discount` по услуге/приёму), а не по
номиналу `SellableItem`. Если effective ≠ стандартной цены услуги → белая строка:
`note` = причина (скидка/тех.персонал), `unitPrice`/`total` = фактическая.
Заодно `standard.total` и `lessons.totals.total` должны считаться по фактической
оплате, иначе выручка отчёта завышена.

## Вторичная причина — фильтр «только оплаченные (paid_*>0)» отсекает 100%-скидку

Decision #3: в отчёт входят только занятия с `paid_*>0`. Занятие со **100%
скидкой** имеет `paid_* = 0` (вся сумма ушла в `discount`, `debt=0`) — см.
связанный баг 100%-скидки (статус `paid`, `paid*=0`). Такое занятие **проведено и
закрыто скидкой**, но фильтр его выкидывает.

**Нужно решение заказчика/бэка:** скидочные (в т.ч. 100%) занятия должны
**входить** в отчёт. Предлагаю критерий охвата: занятие **закрыто** за этот день —
`paid_* > 0` **ИЛИ** `discount > 0` (debt=0 за счёт скидки) **ИЛИ** покрыто
абонементом. Тогда `unitPrice`/`total` белой строки = фактически начисленное за
вычетом скидки (может быть 0 при 100% — подтвердите, показывать ли 0 или номинал).

## Открытые вопросы

1. Подтвердите фикс: «исключение» = занятие с effective-ценой
   (`total_amount − discount`) ≠ стандартной цене услуги; `standard`/`totals`
   считать по фактической оплате, а не по номиналу.
2. Для белой строки скидочного занятия `unitPrice` = фактически оплачено (со
   скидкой). На образце исключения показывают фактическую (600 при стандартной 1000).
   Подтверждаете?
3. 100%-скидка (paid=0, debt=0 за счёт скидки): включать в отчёт белой строкой
   (с суммой 0 или номиналом?), или такие в «Занятия» не нужны?

## Связано

- `docs/backend-requests-2026-06-15.md` (контракт daily-lessons, Q1/Q2).
- Баг 100%-скидки: статус выводится из суммы, `paid*=0` при полной скидке.

# Оплата за период: вся выручка на день оплаты, а не размазана по дням приёмов

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25

## Требование заказчика

При оплате «за срок» (запись приёма на период — несколько сессий на разные дни)
вся оплаченная сумма должна признаваться в кассе/отчётах **в день оплаты одним
числом**, а не распределяться по дням, на которые стоят приёмы.

Сейчас: «оплата идёт по другим дням» — клиент заплатил всю сумму сегодня, а в
отчётах она появляется частями в дни будущих/прошлых сессий.

## Как сейчас устроено (фронт)

Запись «на период» (`HomeAddAppointmentDrawer`, режим «На период»):
1. создаёт **N приёмов — по одному на каждую дату** периода (один приём = одна
   сессия на своём `appointmentAt`);
2. предлагает оплату за весь период (`PaymentSidebar`, bulk-режим) — сумма
   **делится поровну между всеми N приёмами** (`distributeAmount`) и каждый приём
   PATCH-ится своей долей:
   ```
   PATCH /api/v1/appointments/{id}/  { paidCash: share, paidCard: share, discount: share, ... }
   ```

Так как `paid_*` лежат на каждом приёме, а приёмы стоят на разных датах,
отчёты (`financial-monthly`, `cashbox/summary`, `daily-summary`) разносят выручку
**по дате приёма** → сумма размазывается по дням срока. Это и есть жалоба.

## Что нужно

Признавать оплату за период **в день фактической оплаты** (TZ Asia/Bishkek),
одной суммой в кассе/выручке, при этом:
- приёмы периода остаются **оплаченными** (без долга);
- это должно сходиться в `cashbox/summary`, `financial-monthly` (`days[]`/`totals`),
  `daily-summary` (`income`, наличка).

Похоже на модель абонемента из `docs/subscription-service-spec.md` (покупка =
одна продажа в день оплаты; сессии покрыты).

## Открытые вопросы (нужно решение бэка — не закладывать молча)

1. **Механизм даты.** Как бэк свяжет выручку с днём оплаты?
   - (а) добавить дату/таймстамп оплаты на приём (`paidAt`) и в кассовых/выручка-
     отчётах бакетировать по `paidAt`, а не по `appointmentAt`; либо
   - (б) отдельная сущность «оплата за период» (one payment → N appointments),
     дата = день оплаты, отчёты берут выручку из неё.
   Какой вариант предпочтителен в текущей модели данных?
2. **Сигнал от фронта.** Что фронт должен прислать, чтобы бэк понял «это оплата за

# Ребёнок сотрудника: авто-удержание стоимости услуги с родителя-специалиста

[ПРИОРИТЕТ: ВЫСОКИЙ] · дата: 2026-06-25

## Требование заказчика

Если приём оформлен на **ребёнка сотрудника** и его «пробивают» (проводят оплату),
стоимость услуги должна **автоматически** идти **удержанием (`kind=deduction`) на
сотрудника-родителя** — т.е. услуга ребёнку покрывается из зарплаты родителя, а не
оплачивается кэшем.

## Данные уже есть (проверено вживую)

У клиента (`/api/v1/clients/{id}/`) есть всё необходимое:
```
isEmployeeChild: true
employeeParent: "<employee-uuid>"        // НА КОГО вешать удержание
employeeParentName: "Кадыркулов Азамат..."
employeeChildDiscountPercent: 100 | 40 | 0   // может быть 0 — скидки может НЕ быть
```
Живые примеры (Манас): Орункулов Аслан → родитель Кадыркулов Азамат (pct=100);
Увайдилаев Эламан → Жорокулов Адилет (pct=40); Алиев Ариет → Алиев Эрмек (pct=0).
Сейчас фронт по `isEmployeeChild` только форсит скидку `employeeChildDiscountPercent`
в окне оплаты (`PaymentSidebar`).

## Финансовая модель (решение заказчика: «скидка + удержание на остаток»)

При проведении приёма ребёнка сотрудника по каждой услуге:
```
discount   = service_price * employeeChildDiscountPercent / 100   // льгота центра (может быть 0)
deduction  = service_price − discount                              // остаток → на родителя
```
- ребёнок **не платит кэшем** — приём закрывается (debt = 0);
- на `employeeParent` создаётся `payroll-transaction kind=deduction` на сумму
  `deduction` (при pct=100 → deduction = 0, удержание не создаём);
- **скидки может не быть** (pct=0) → удержание = полная цена услуги.

## Почему на бэке

- Идемпотентность: на фронте есть «Перепровести оплату» — повторный вызов не должен
  плодить дубликаты удержаний. Нужна привязка удержания к приёму/услуге и
  update-or-create.
- Атомарность и источник правды (как в `docs/subscription-service-spec.md`): статус
  оплаты, касса, отчёты, ЗП должны сходиться на сервере.

## Открытые вопросы (нужно решение бэка/заказчика — не закладывать молча)

1. **Идемпотентность/привязка.** Удержание привязывать к `appointment`(+`service`)?
   При перепроведении — update; при отмене приёма / возврате — удержание
   **сторнировать/удалять**. Подтвердите механизм.
2. **Несколько услуг в приёме.** Удержание на КАЖДУЮ услугу отдельной транзакцией
   (с примечанием), или одно суммарное на приём? Предлагаю по услуге (трассируемо).
3. **`affectsMonth` / `branch`** удержания = месяц/филиал приёма. Подтвердите.
4. **Примечание** транзакции — предлагаю авто: «Услуга ребёнку: <услуга> (<ФИО ребёнка>)».
5. **Выручка/касса.** Ребёнок платит 0, деньги «возвращаются» через невыплату
   родителю. Как признаётся услуга в отчётах: выручка 0 + удержание в ЗП (центр
   удерживает из зарплаты)? Или услуга считается выручкой? Это влияет на
   financial-monthly / daily-summary / payroll. Нужна явная семантика, чтобы касса и
   ЗП сходились (двойного счёта быть не должно).
6. **Триггер.** Создавать удержание при проведении ОПЛАТЫ приёма (а не при создании
   записи), чтобы незакрытые/отменённые приёмы не порождали удержаний. Подтвердите.
7. **Можно ли переопределить вручную** (если кассир всё же хочет взять кэш с ребёнка)?
   Предлагаю: авто по умолчанию, но не блокировать ручную оплату.

## Влияние на фронт (после контракта)

`PaymentSidebar`: для `isEmployeeChild` показывать, что остаток уйдёт удержанием на
`employeeParentName` (информационно), не требовать кэш; фактическое создание
удержания — на бэке при проведении. Скидку (`employeeChildDiscountPercent`) фронт уже
подставляет.

# Отчёты: количество приёмов включает ОТМЕНЁННЫЕ (256 vs реальные 255)

[ПРИОРИТЕТ: СРЕДНИЙ] · дата: 2026-06-25 · эндпоинт `GET /api/v1/reports/financial-monthly/`

> **КОРНЕВАЯ ПРИЧИНА найдена (живой GET, Главный 2026-06):**
> - `financial-monthly`: `totals.appointmentsCount=256`, `summaryCards.appointments=256`,
>   `sum(days[].appointmentsCount)=256` — всё включает отменённый приём;
> - `appointments-aggregated`: **255** записей, статусы только `paid`(214)+`scheduled`(41),
>   **без `cancelled`**;
> - raw `appointments` за июнь (Бишкек): 256, из них **1 `cancelled`** (15.06).
>
> **256 − 255 = ровно 1 отменённый приём.** `financial-monthly.appointmentsCount`
> **считает отменённые**, а «реальные» (проведённые) = 255. На момент жалобы заказчика,
> вероятно, `totals` ещё исключал отменённый (255), а `summaryCards` включал (256) →
> «отчёты 256 / таблица 255». Сейчас оба поля = 256 (бэк свёл их, но в сторону
> ВКЛЮЧЕНИЯ отменённых — спорно).
>
> **Вопрос/правка бэку:** «Количество занятий/детей» в отчёте — должно ли включать
> **отменённые** приёмы? Логично НЕТ (занятие не состоялось) → `appointmentsCount`
> должен исключать `status=cancelled` (и, возможно, `no_show`/`not_came`), тогда
> будет 255, как в `aggregated`. Уточните и приведите `financial-monthly` к этому.
> Фронт сведён к одному полю (`totals`), так что после бэк-правки число просто станет 255.

## Проблема

В ответе `financial-monthly` два поля считают одно и то же («количество
записей/приёмов за месяц»), но дают **разные значения**:

- `summaryCards.appointments` = **256**
- `totals.appointmentsCount`   = **255**

Фронт показывал их в двух местах страницы «Отчёты» (карточка «Услуги → N
записей» брала `summaryCards.appointments`; строка «ИТОГО» таблицы — 
`totals.appointmentsCount`), из-за чего заказчик видел 256 вверху и 255 в
таблице. На фронте мы временно свели оба места к `totals.appointmentsCount`
(он сходится с поднеёвной разбивкой `days[].appointmentsCount`), но корень — на
бэке: два агрегата одного показателя расходятся.

Воспроизведение: открыть «Отчёты» за месяц с расхождением (наблюдалось на
256/255), сравнить карточку «Услуги» и итог колонки «Записи».

## Вопросы

1. **Почему `summaryCards.appointments` и `totals.appointmentsCount` различаются?**
   Ожидается, что `totals.appointmentsCount == Σ days[].appointmentsCount`.
   `summaryCards.appointments` считается отдельным запросом? По другому фильтру
   статусов / диапазону дат / часовому поясу?
2. **Какое из чисел каноническое** (которое показывать пользователю)?
3. Разница ровно в 1 — типичный признак **пограничного приёма**: приём на стыке
   суток (UTC vs Asia/Bishkek) попал в месяц на уровне summaryCards, но в
   поднеёвные бакеты `days[]` не попал (или попал в день вне месяца). Либо приём
   с особым статусом (cancelled / no_show / not_came), который один агрегат
   учитывает, а другой — нет. Проверьте именно эти два сценария.
4. **`summaryCards.procedures` vs `totals.proceduresCount`** — та же пара полей,
   вероятно та же рассинхронизация. Свести по тому же правилу.

## Желаемое

Оба поля должны давать одно число по одной и той же бизнес-логике (статусы,
диапазон, TZ). Если поля сознательно разные (напр. summaryCards = все приёмы,
totals = только с активностью) — задокументировать различие, тогда фронт выберет
нужное осознанно.

## Что НЕ требуется менять

Формат ответа, прочие поля `totals`/`summaryCards`, поднеёвная разбивка `days[]`.
Нужна только согласованность счётчиков `appointments`/`procedures`.
