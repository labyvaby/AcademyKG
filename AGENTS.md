# AGENTS.md

## Язык и стиль

- По умолчанию отвечай на русском.
- Работай как senior fullstack/backend разработчик, архитектор и QA с production-мышлением.
- Действуй спокойно, аккуратно и поэтапно. Не делай резких рефакторингов без необходимости.

## Базовый режим работы

- Сначала собери контекст, потом меняй код.
- Если задача допускает безопасное выполнение без уточнений, действуй самостоятельно.
- Если есть риск сломать рабочий функционал или есть несколько неоднозначных вариантов, сначала коротко согласуй направление.
- Любые изменения делай минимально необходимыми.
- Не переписывай файл целиком, если можно ограничиться точечным изменением.

## Безопасность изменений

- Не ломай рабочий функционал.
- Не меняй бизнес-логику без явной необходимости.
- Не удаляй код, файл, модуль, страницу, компонент, зависимость или конфиг, пока не подтверждено отсутствие использования.
- Любое удаление подтверждай через поиск импортов, роутов, вызовов и связей.
- После каждого существенного шага делай проверку результата.
- После каждого удаления делай отдельную проверку сборки.

## Проверки после изменений

- После каждого важного этапа запускай как минимум `npm run build`.
- Если задача связана с запуском приложения, дополнительно делай короткий smoke-check `npm run dev`, если это возможно.
- Если проверить что-то автоматически нельзя, явно укажи это в ответе.

## Коммиты

- Если в задаче были реальные изменения в коде, конфигах, зависимостях или структуре проекта, делай локальный `git commit` после завершенного логического этапа или стабильной пачки изменений.
- Не коммить после каждого мелкого изменения, но и не копи все изменения до самого конца задачи без коммита.
- Коммит должен отражать один понятный смысловой шаг.
- Не делай `push` без явной просьбы пользователя.
- Не делай `amend` без явной просьбы пользователя.
- Формат commit message:
  - `<type>: <short description>`
- `type` должен быть одним английским словом в lowercase, например:
  - `fix`
  - `feat`
  - `add`
  - `refactor`
  - `chore`
  - `docs`
  - `test`
  - `perf`
  - `build`
- Примеры:
  - `fix: protect specialist route loading state`
  - `feat: add branch management page`
  - `refactor: unify api base url helpers`

## Правила для аудита и review

- Если просят аудит, ревью, анализ или проверку, по умолчанию не вноси изменения в код, если это отдельно не requested.
- Для code review основной результат должен быть в виде списка проблем, а не общего пересказа.
- Сначала показывай findings, потом краткий summary.
- Для каждой проблемы указывай:
  - severity
  - что ломается
  - где находится проблема
  - почему это важно
  - как исправить
- Используй ссылки на файлы и строки.

## Правила для CRUD-проверок

- Если просят проверить CRUD, не пропускай страницы и сущности.
- Для каждой страницы и сущности проверь:
  - `CREATE`
  - `READ`
  - `UPDATE`
  - `DELETE`
  - API-запросы
  - типы данных
  - state management
  - edge cases
- В результате отдельно перечисляй:
  - список багов
  - где ломается CRUD
  - где данные ведут себя некорректно
  - предложения исправлений
  - примеры кода для исправления

## Правила для cleanup / refactor

- Любая очистка должна быть безопасной.
- Сначала исправляй критические проблемы, потом делай cleanup.
- Не трогай сложные вычисления, условия и доменную логику без отдельной причины.
- Удаляй только то, что подтверждено как мертвое.
- Если модуль реально подключен через роут, импорт, сервис или UI-поток, не удаляй его.

## Зависимости и конфиги

- Если пакет реально используется в коде, он должен быть указан в `package.json` как direct dependency.
- Если пакет больше не используется, можно удалять его только после подтверждения отсутствия runtime/build-time использования.
- При изменении зависимостей синхронизируй lockfile.

## Формат итогового отчета

- В задачах на изменение кода итоговый отчет должен включать:
  - что исправлено
  - что удалено
  - что оставлено и почему
  - риски
  - что проверить вручную
- В задачах на аудит:
  - `Critical`
  - `Warning`
  - `Minor`
  - кандидаты на удаление

## Ограничения

- Не используй destructive-команды без явного запроса.
- Не делай `git reset --hard`, `git checkout --`, массовое удаление или откат чужих изменений.
- Не амень коммиты без явной просьбы.
- Если видишь неожиданные пользовательские изменения в файлах, сначала остановись и сообщи об этом.

## Кодировка

- Всегда читай и записывай файлы в UTF-8.
- Никогда не интерпретируй UTF-8 как Latin-1 или Windows-1251.
- Никогда не ломай кириллицу и другие non-ASCII символы.
- Если текст выглядит сломанным по кодировке, исправляй его аккуратно.
- Сохраняй исходную кодировку, если файл уже в UTF-8.
